= Stream Processing Architecture
:revdate: 2026-03-06

== 1. Model & Storage

Модель -- это текущее состояние мира с точки зрения BPMN-движка. Модель хранится в хранилище. Модель хранения описана в виде protobuf.

Хранимые сущности делятся на две категории:

**Иммутабельные** (создаются один раз, не изменяются):

- Process definition (deployed BPMN)
- Decision definition (DMN)
- Form definition
- Deployment record

**Мутабельные** (изменяют состояние в процессе жизни):

- Process instance (CREATED -> ACTIVE -> COMPLETED/TERMINATED)
- Element instance (токен на конкретном BPMN-элементе)
- Variable (значение меняется в рамках scope)
- Job (CREATED -> ACTIVATED -> COMPLETED/FAILED)
- Timer (ожидает -> сработал)
- Message subscription (открыта -> скоррелирована)
- Incident (CREATED -> RESOLVED)

== 2. Partitioning

Данные хранятся в разрезе партиций. Каждая партиция изолирована от других -- как по данным, так и по обработке. Партиция является единицей параллелизма.

**Routing:**

- При создании process instance выбирается наименее загруженная партиция (по длине очереди намерений).
- Все последующие события в рамках этого instance обрабатываются на той же партиции.
- Сущности не мигрируют между партициями.

**Ключи:**

Ключи сущностей -- `uint64`, старшие 8 бит кодируют номер партиции, младшие 56 бит -- sequence:

----
| partition (8 bit) | sequence (56 bit) |
----

Это даёт до 256 партиций и ~72 квадриллиона ключей на каждую. По любому ключу (job, variable, element instance) партиция определяется за O(1) без lookup-таблиц.

== 3. Command Processing

Внешний мир общается с движком с помощью команд. Команда при поступлении в партицию превращается в намерение (intent). У намерения есть поведение, которое описывает как должно измениться состояние внутри движка.

**Цепочка обработки:**

----
Command (external) -> Intent -> Behavior -> State changes + new Intents
----

Поведение намерения может:

- Изменить состояние сущностей (process instance, element instance, variable, job, ...)
- Добавить новые намерения в конец очереди партиции

**Последовательная обработка:**

Партиция обрабатывает намерения последовательно, одно за другим. Каждое намерение атомарно -- либо полностью выполнено, либо нет. Между намерениями состояние всегда консистентно.

NOTE: Цепочка намерений не рекурсивная (stack), а очередь (queue). Новые намерения добавляются в конец очереди.

**Error handling:**

[cols="1,1,1"]
|===
| Тип намерения | При ошибке | Логика

| Внутреннее (порождено другим намерением)
| Incident
| Ошибка внутреннего намерения -- баг или невалидное состояние, retry не поможет

| Внешнее (порождено командой от клиента)
| Retry с backoff, затем incident
| Внешние команды могут быть временно невалидны, retry даёт шанс на восстановление
|===

== 4. Variables & Scope

Переменная -- отдельная сущность, связанная с process instance и scope.

**Scope** = element instance (process, subprocess, multi-instance body).

- При входе в scope: переменные могут копироваться из родительского scope (input mappings или наследование).
- Внутри scope: работа только со своими переменными, изоляция от родителя.
- При выходе из scope: переменные могут пропагироваться в родительский scope (output mappings).

Это даёт изоляцию: subprocess не может случайно затереть переменную процесса, только явно через output mapping.

== 5. Events & Export

Любое изменение данных приводит к образованию события, которое публикуется в очередь на экспорт.

**Текущий подход: Event Notification.**

- Состояние в хранилище -- source of truth.
- События генерируются как побочный эффект изменения состояния.
- События предназначены для внешних потребителей (audit, analytics, monitoring).

WARNING: Архитектурно необходимо заложить возможность переключения на Event Sourcing (лог записей = source of truth, состояние восстанавливается replay-ем). Интерфейс генерации событий должен быть абстрагирован для подмены реализации.

== 6. Message Correlation

Модель: broadcast по всем партициям.

**Поток:**

1. Приходит `PublishMessage(name, correlationKey, payload, TTL)`.
2. Сообщение рассылается на все партиции.
3. На каждой партиции: поиск открытых message subscriptions с matching `name` + `correlationKey`.
4. Если найдена подписка -- корреляция (активация catch event, передача payload).
5. Если подписка не найдена -- сообщение буферизуется на TTL. Если подписка появится позже -- скоррелируется.
6. По истечении TTL -- drop.

**Дедупликация:** отсутствует. Один correlationKey может активировать подписки на нескольких партициях. Клиент отвечает за уникальность.
